CSRF Quick Notes · 廣東話

60-minute Lab：先篩選真正會改資料嘅 Endpoints；唔需要逐個 API 都起 PoC。建議 CSRF 初步評估限制喺 5–8 分鐘。

① Prioritise

優先睇更改 Email、Profile、Address、Account Setting 嘅 Request。GET 通常只讀，但如果 GET 修改 State，都值得檢查。

② Check Authentication

睇 Cookie: session=... 定係 Authorization: Bearer ...。Browser 可能自動帶 Cookie；普通 HTML Form 唔會自動加 Bearer Header。

③ Check Defences

檢查 CSRF Token、Origin/Referer、Cookie SameSite、Sec-Fetch-Site。刪除 Token 喺 Repeater 成功唔等於已證實 CSRF。

④ Confirm the result

喺已登入測試 Browser 開另一個來源嘅 PoC；睇 Burp HTTP History 係咪帶 Cookie，返回 App 核實 State 真係變咗。

How to interpret the outcome

ObservationConclusion
HTTP request appeared in BurpOnly proves the browser sent a request.
Browser included session cookie and test state changedStrong evidence of exploitable CSRF when the action was unauthorised by user intent.
No Cookie or rejected 403Inspect SameSite, Origin, CSRF Token and the selected test origin.
PATCH / JSON / Bearer-onlyNormal form not sufficient. CORS preflight and custom headers may prevent exploitation.

Quick procedure

  1. Capture one legitimate state-changing request with a synthetic test account.
  2. Paste into this page and review the target, original authentication headers and omitted CSRF fields.
  3. Click generated GET link or POST form manually in the signed-in Browser.
  4. Inspect the actual Request in Burp and confirm the application state, not only HTTP status.
  5. Write confirmed evidence and limitations in the Report Builder.
Opening downloaded HTML via file:// can produce Origin: null; GitHub Pages has a different Origin. Both Browser cookie restrictions and application Origin checks can alter the result. A failed PoC does not necessarily prove the endpoint is secure.
